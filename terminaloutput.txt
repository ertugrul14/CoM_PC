★ Insight ─────────────────────────────────────
  Reading the architecture before diagnosing is critical here — the code already contains a counterfactual rollout framework, so the question isn't "does it exist?" but "what limits its reliability as a causal network-impact estimator?"  
  ─────────────────────────────────────────────────

  Here's the full picture. The good news first: Step 11 already does exactly this — it runs a baseline and a treated autoregressive rollout, computes delta across all 3,975 streets, and reports top affected, spatial neighbours, semantic  
  neighbours, diffusion, and rebound. The framework is built.

  What limits or prevents it from being a reliable causal network-impact predictor:

  ---
  1. The model was trained as a forecaster, not a causal model

  This is the most fundamental constraint. The MultiGCN learned to predict t+1 from the last 24h of observed data. It learned correlational patterns from the cube — streets that co-vary in real life. When you clamp a street's features    
  (e.g., occ_rate = 0 for pedestrianise), the GCN propagates that signal through the graph, but what it propagates reflects learned co-occurrence, not a causal mechanism.

  Concretely: if street A and street B always have similar pedestrian flow (because of shared land use), the model will show a large delta on B when you change A — not because B is causally affected by A, but because the model learned    
  they move together.

  ---
  2. Parking spillover is supervised on only 138 / 3,975 streets (~3.5%)

  # step_09_train.py:426
  park_loss = criterion(
      pred_park[:, parking_mask, :],   # ← only 138 streets contribute gradient
      y_park[:, parking_mask, :],
  )

  The parking head has zero training signal for the remaining 3,837 streets. Their parking predictions are unconstrained extrapolations from the shared GCN+GRU backbone. This means:
  - The parking displacement effect you see on non-sensor streets is pattern-inferred, not learned from data
  - You can trust parking network deltas only on the 138 parking_mask streets

  ---
  3. Parking values in the cube are very low (~12.5% max occupancy)

  From current_state.md known issues: "Cube parking values are very small (~12.5% max)." The parking head was trained almost entirely in the range [0, 0.125]. Interventions like pedestrianise (setting target to 0) or restrict_park (e.g., 
  setting to 0.8) push the model far outside its training distribution, making spillover predictions unreliable.

  ---
  4. Graph edges are fixed — topology cannot change

  From step_11's own design assumptions (line 38):

  ▎ "The intervention modifies node features only — graph edges are unchanged. In reality, pedestrianisation may alter network connectivity; this is not modelled."

  Pedestrianising a street often changes routing — vehicles can't pass through, creating detours. The spatial graph (k-NN, Gaussian kernel) was built on physical proximity and is fixed at build time. The model cannot represent a street   
  becoming a dead end or losing its role as a through-route.

  5. Only ped_flow is fed back autoregressively for non-sensor streets

  # step_11_scenario.py:481-486
  next_row[:, FI_PED_FLOW] = pred_ped_norm              # all streets — autoregressive
  if parking_mask is not None:
      next_row[parking_mask, FI_OCC_RATE] = pred_park_norm[parking_mask]  # sensor streets only

  For the 3,837 non-sensor streets, the parking occupancy in the sliding window is always real historical data from the cube, never the model's prediction. So parking spillover cannot propagate autoregressively through non-sensor streets 
  — only pedestrian effects do.
